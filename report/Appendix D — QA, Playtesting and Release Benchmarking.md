# QA, Playtesting and Release Benchmarking for a Solo-Dev Mobile Puzzle Game

**Purpose.** Benchmark a one-person mobile puzzle-game "AI factory" against how best-in-class studios actually test, tune and ship games; against the research state of the art in AI-assisted QA; and against established games-user-research (GUR) practice. Every factual claim below links to the exact page that was fetched and states it. Where a claim could not be verified from a fetched source it is marked **n.a.**

**System under benchmark (the "factory"), restated for reference:**

| Layer | What it does |
|---|---|
| (a) Tools-side generator + BFS solver | Proves all 40 levels solvable, computes optimal "par"; per-level seeds make regeneration byte-identical |
| (b) Commit gate (~2 min) | Headless Chromium bot replays every level's optimal solution through the real engine, asserts moves/par/limit; 109 named regression checks (star bands, difficulty sawtooth, theme contrast, undo/rescue, hint latency <150 ms, reduced-motion, ad-slot grants, modal dismissal, daily-puzzle determinism across 2 browser contexts, share-string regex + spoiler assertions, engine-vs-tools rule-parity oracle over 200 random positions, bundle freshness, zero-network) |
| (c) iOS XCUITest | Launches app with autoplay flag; in-app bot beats all 40 levels |
| (d) Two AI personas | "Critic" first-play reviewer → scored review + notes `{area, severity, text}`; adversarial "breaker" → REPRO/EXPECTED/ACTUAL bug reports |
| (e) Developer pass | Triage every note DO NOW / DESIGN CHANGE / SKIP, fix root cause, add a regression check per fix, rerun both bots |
| Not present | Live telemetry, human external playtesters, store release |

## 1. How best-in-class studios test and tune games

### 1.1 Automated test bots, smoke tests and build-verification gates

The reference implementation of "bots gate the build" is Riot's **Build Verification System** for *League of Legends*. Riot reports well over 100 code and content check-ins per day and a new patch every two weeks; the BVS runs roughly **5,500 test cases in about 18 minutes for every new build**, roughly **100,000 test cases per day**, reports results within about an hour of check-in, and finds approximately **50% of all critical- or blocker-level bugs**; bugs found by automation are resolved **eight times faster** than the average bug, and misses are attributed to coverage gaps rather than bad tests ([Riot Games, "Automated Testing for League of Legends"](https://www.riotgames.com/en/news/automated-testing-league-legends)).

Riot's *Legends of Runeterra* CI/CD pipeline shows the mobile-relevant shape: one pipeline builds Windows, Android and iOS artifacts in a single run, runs ~**100 pipeline runs a day** and **2,000–3,000 builds a month** at an average runtime of about **60 minutes**, with several hundred functional tests executing in a few minutes because the game runs at **10× speed** and tests are parallelized; hash-based build plans skip unchanged artifacts, and public releases ship "every few weeks, with hotfixes along the way" ([Riot Games, "The Legends of Runeterra CI/CD Pipeline"](https://www.riotgames.com/en/news/legends-runeterra-cicd-pipeline)).

At GDC 2019 Ubisoft Reflections described **"Client Bots"** for *The Division* — AI that takes control of the player, mimics human input, and reports issues including missions that cannot be completed plus performance statistics; the talk explicitly covered "best practices for content creation to facilitate automation" ([GDC, "See how Ubisoft tested The Division with automated players"](https://gdconf.com/article/see-how-ubisoft-tested-the-division-with-automated-players-at-gdc-2019/)). Rare's *Sea of Thieves* talk the same year covered a bespoke framework letting any team member author automated tests, the types of tests built, what coverage level was appropriate, and how to keep tests reliable on a live, evolving game ([GDC, "Sea of Thieves devs share automated testing tips"](https://gdconf.com/article/sea-of-thieves-devs-share-automated-testing-tips-at-gdc-2019/)). An ongoing cross-studio **Automated Testing Roundtable** runs at GDC with daily themes of Process, Legacy and Implementation, explicitly open to "all experience levels, budgets, genres, and platforms" ([Automated Testing at GDC, ATIG](https://atig.dev/gdc/)).

King's public position is a **playtesting bot as design co-pilot**: it tells designers whether a level is playable, how much shuffle it has, whether it delivers the intended challenge, and its difficulty; where a level misses intent, designers state criteria and the bot proposes refinements. The bot is trained on "millions and millions of states" to pick the action a *human* would most likely take rather than the optimal one, and King validates it by checking that bot difficulty estimates track real difficulty data in a linear pattern. Reported impact: **95% fewer manual tweaks** and level tweaks **50% faster** ([GamesIndustry.biz, "How King is using AI to speed up development of new Candy Crush levels"](https://www.gamesindustry.biz/how-king-is-using-ai-to-speed-up-development-of-new-candy-crush-levels)).

### 1.2 Deterministic replay

Riot spent close to a year with multiple engineers making *League of Legends* server state "gameplay deterministic" — not 100% memory-snapshot parity, but the gameplay-essential state governing critical interactions. Their operational definition: a divergence is discovered by comparing runtime state across multiple executions with fixed inputs, and "software divergences are the product of unexpected inputs". The payoff included tools to **record, play back and validate real-world games** plus improved robustness and dead-code removal ([Riot Games, "Determinism in League of Legends: Implementation"](https://www.riotgames.com/en/news/determinism-league-legends-implementation)).

### 1.3 Soak / monkey / fuzz testing

Android ships the **UI/Application Exerciser Monkey**, which fires pseudo-random clicks, touches, gestures and system events at an app; it can be constrained to specific packages, stops and reports on crashes, unhandled exceptions or ANRs, and — critically for reproducibility — `-s <seed>` makes re-runs generate the identical event sequence, so stress testing is "random yet repeatable" ([Android Developers, UI/Application Exerciser Monkey](https://www.dre.vanderbilt.edu/~schmidt/android/android-4.0/out/target/common/docs/doc-comment-check/guide/developing/tools/monkey.html)).

### 1.4 Device farms and compatibility matrices

**Firebase Test Lab** runs apps on real production devices in a Google data center plus virtual Android devices on Arm hosts, with test matrices configured across devices, OS versions, locales and screen orientations, and integrates with the Firebase console, Android Studio, `gcloud` and CI ([Firebase Test Lab](https://firebase.google.com/docs/test-lab)). Test types are **instrumentation tests** (Espresso/UI Automator with explicit assertions), **Robo test** (automatic UI exploration, no code) and **Game Loop test**, which uses a game "demo mode" to simulate player actions natively in the engine — with multiple labelled loops per execution. Tests are capped at **45 minutes on physical devices / 60 minutes on virtual**, any uncaught exception fails the test, and Test Lab can be used at no cost for APKs published to the Play alpha or beta channels ([Firebase Test Lab — get started, Android](https://firebase.google.com/docs/test-lab/android/get-started)).

Google Play's **pre-launch report** applies the same machinery automatically: on each bundle/APK upload and on saving a production release, the app is installed across a set of lab devices, launched and **crawled for several minutes** with typing, tapping and swiping; it reports stability, Android compatibility, performance and accessibility issues, and gives a launch recommendation. Crawls can be steered with a **Robo script** or replaced with **game loops** for OpenGL games, and up to three deep links can be exercised ([Play Console Help, "Use a pre-launch report to identify issues"](https://support.google.com/googleplay/android-developer/answer/9842757?hl=en)). The report's contents include per-device stack traces, screenshots and video, non-SDK (restricted / soon-restricted / unsupported) interface warnings, and per-device-model performance metrics including **average FPS (game-loop tests only)**, average CPU and average network bytes/second ([Play Console Help, "Understand your pre-launch report"](https://support.google.com/googleplay/android-developer/answer/9844487?hl=en)).

Commercial performance coverage is dominated by **GameBench**, which measures frame rate, CPU, GPU, real-time FPS, normal and "big" janks, device and battery temperature across Android and iOS, from APK/IPA builds, via automation, device farms and soft launch, with a shared dashboard for comparing builds, devices and rival games ([GameBench](https://www.gamebench.net/)). modl.ai's tool census also names **LambdaTest** (3,000+ real devices/browsers/OS for compatibility), **Lionbridge Games** (localization QA) and **QAwerk** (mobile game QA services), alongside its own **modl:test** AI bots that explore game environments, detect bugs/crashes/perf issues, integrate with Unity, Unreal and custom engines via API, and plug into CI/CD ([modl.ai, "The Big List of Game Testing Tools and Services"](https://modl.ai/game-testing-tools)).

### 1.5 Crash/ANR gates and Google Play vitals thresholds

These are hard, published numbers and the single clearest external quality bar for a mobile game:

| Metric | Threshold | Scope | Consequence |
|---|---|---|---|
| User-perceived crash rate | **1.09%** | Whole app title | Stay below to maximize Play visibility ([Android Developers Blog](https://android-developers.googleblog.com/2022/10/raising-bar-on-technical-quality-on-google-play.html)) |
| User-perceived ANR rate | **0.47%** | Whole app title | Same ([Android Developers Blog](https://android-developers.googleblog.com/2022/10/raising-bar-on-technical-quality-on-google-play.html)) |
| Per-device crash or ANR rate | **8% at launch**, expected to tighten in H1 2023 | Per phone model | Reduced visibility for users on that model; exclusion from some discovery surfaces; possible store-listing warning ([Android Developers Blog](https://android-developers.googleblog.com/2022/10/raising-bar-on-technical-quality-on-google-play.html)) |
| Recommended per-phone stability target | **no worse than 2%** | Per phone model | Developer guidance ([Android Developers Blog](https://android-developers.googleblog.com/2022/10/raising-bar-on-technical-quality-on-google-play.html)) |

Play states that core vitals affect discoverability, that apps exceeding a bad-behavior threshold are "likely to be less discoverable", that users on bad-behaving device models are steered away, that a store-listing warning may be shown, and that Play generally evaluates the **last 28 days** of data but may act sooner on a spike ([Play Console Help, "Monitor your app's technical quality with Android vitals"](https://support.google.com/googleplay/android-developer/answer/9844486?hl=en)). Store-listing warnings began **30 November 2022** ([Android Developers Blog](https://android-developers.googleblog.com/2022/10/raising-bar-on-technical-quality-on-google-play.html)).

ANR triggers are concrete engineering budgets, not vibes: input dispatch not handled within **5 seconds**, `Service.startForeground` not called within **5 seconds**, foreground broadcast receivers exceeding **5 seconds** ([Android Developers, ANRs](https://developer.android.com/topic/performance/vitals/anr)). For production alerting, **Crashlytics velocity alerts** fire when, inside a **30-minute window**, an issue exceeds a session-percentage threshold (default **1%**) and a minimum impacted-user count (default **25 users**) with at least 10 users in the period; increasing-velocity alerts are **off by default** ([Firebase, "Customize velocity alerts"](https://firebase.google.com/docs/crashlytics/velocity-alerts)).

### 1.6 Apple App Store review pitfalls

Apple states that, on average, **over 40% of unresolved review issues relate to Guideline 2.1 App Completeness** — crashes, placeholder content, incomplete information — with broken links (2.1/5.1), inaccurate screenshots (2.3), privacy-policy and data-access problems (5.1), and "not enough lasting value" (4.2) also on the common list ([Apple, "App Review — Common rejections"](https://developer.apple.com/app-store/review/rejections/)). The guidelines themselves require pre-submission testing for crashes and bugs, complete and accurate metadata, scrubbed placeholder text and empty websites, on-device testing, and state that "incomplete app bundles and binaries that crash or exhibit obvious technical problems will be rejected"; 4.2 requires lasting entertainment value beyond a repackaged website ([Apple, App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). For a puzzle game with IAP, 3.1.1 requires in-app purchase for unlocking levels, premium content or a full version, forbids alternative unlock mechanisms, requires purchased in-game currency not to expire, and requires **loot-box odds disclosure before purchase** ([Apple, App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)).

### 1.7 Staged rollout, phased release, beta tracks

| Mechanism | Rules |
|---|---|
| **Apple phased release** | 7 days, fixed schedule: day 1 **1%**, day 2 **2%**, day 3 **5%**, day 4 **10%**, day 5 **20%**, day 6 **50%**, day 7 **100%**. Can be paused for a cumulative **30 days** with unlimited pauses; resumes from the paused day. Applies to users with automatic updates on; anyone can still download manually at any time; can be released to all users at any point ([Apple, "Release a version update in phases"](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases/)) |
| **Google Play staged rollout** | Updates only (not first publish); percentage is chosen manually and **does not auto-increase**; users are randomly chosen per release; halting stops further distribution while already-updated users stay on that version; resuming affects the same user set ([Play Console Help, staged roll-outs](https://support.google.com/googleplay/android-developer/answer/6346149?hl=en-GB)) |
| **TestFlight** | Up to **10,000 external testers per app**; public link limits of 1–10,000; external builds require **TestFlight App Review**, first build gets a full review, later builds of the same version may not; up to **six builds per 24 hours** submitted for review ([Apple, "Invite external testers"](https://developer.apple.com/help/app-store-connect/test-a-beta-version/invite-external-testers/)) |
| **Play closed-testing requirement (new personal accounts)** | For personal Play developer accounts created after **13 November 2023**: a closed test with **at least 12 testers continuously opted in for at least 14 days** before applying for production access; Production stays disabled until met ([Play Console Help, app testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en)) |

This last one is a hard gate for a solo dev on a personal account and effectively forces recruiting 12 humans before any release.

### 1.8 Feature flags, remote config and LiveOps

**Unity Remote Config** is namespaced key–value parameters delivered per player via Game Overrides, explicitly marketed for tuning "the game difficulty curve in near real time", gradual feature rollout with impact monitoring, region/segment tailoring, seasonal event on/off switching, and campaign tests of colors/styles/prices — **all without an app update** ([Unity, Introduction to Remote Config](https://docs.unity.com/en-us/remote-config)). **Firebase Remote Config + A/B Testing** provides variants over parameters, targeting chained with AND logic (app version, Analytics audience such as "crashing users", custom user properties), a designated goal metric (Analytics event or conversion funnel), secondary tracking of **crashes, retention and revenue**, and ramping from a small percentage to the full base once a "leader" variant is identified ([Firebase A/B Testing](https://firebase.google.com/docs/ab-testing)).

LiveOps cadence at a named studio with published numbers: **n.a.** (no studio LiveOps calendar was verifiable from a primary source in this research). What is verifiable is release cadence — LoL patches every two weeks ([Riot](https://www.riotgames.com/en/news/automated-testing-league-legends)) and *Legends of Runeterra* releases every few weeks with hotfixes ([Riot](https://www.riotgames.com/en/news/legends-runeterra-cicd-pipeline)).

## 2. State of the art in AI-assisted QA and playtesting

### 2.2 Difficulty and completion-rate prediction

| Work | Venue / year | Finding |
|---|---|---|
| Kristensen, Valdivia, Burelli, *Estimating player completion rate in mobile puzzle games using reinforcement learning* | **IEEE CoG 2020** | Train an RL agent, measure moves needed to complete a level; the **strongest predictor of human completion rate is the number of moves in roughly the best 5% of agent runs**. Agent-to-human differences across levels are "highly correlated" even though the agent does not reach human-level absolute performance ([arXiv:2306.14626](https://arxiv.org/abs/2306.14626)) |
| Kristensen, Valdivia, Burelli, *Statistical Modelling of Level Difficulty in Puzzle Games* | **IEEE CoG 2021** (DOI 10.1109/CoG52621.2021.9619050) | Argues probability-of-completion is too thin a definition of difficulty; models the **distribution of actions performed within a level** with a parametric statistical model. Fitted on *Lily's Garden* (Tactile Games) data; describes/explains difficulty in "a vast majority of the levels" ([ACM DL](https://dl.acm.org/doi/10.1109/CoG52621.2021.9619050)) |
| Kristensen, Guckelsberger, Burelli, Hämäläinen, *Personalized Game Difficulty Prediction Using Factorization Machines* | ACM, issued 2022-10-28 (DOI 10.1145/3526113.3545624) | Personalized difficulty prediction via factorization machines; numeric accuracy not extractable from the fetched page — **n.a.** ([ACM DL](https://dl.acm.org/doi/fullHtml/10.1145/3526113.3545624)) |
| Roohi, Guckelsberger, Relas, Heiskanen, Takatalo, Hämäläinen, *Predicting Game Difficulty and Engagement Using AI Players* | 2021, DOI 10.1145/3474658 | Title/authors/year confirmed; method and correlation values not stated on the fetched page — **n.a.** ([ACM DL](https://dl.acm.org/doi/abs/10.1145/3474658)) |
| Kristensen & Burelli, *Difficulty Modelling in Mobile Puzzle Games: An Empirical Study on Different Methods to Combine Player Analytics and Simulated Data* | 2024, [arXiv:2401.17436](https://arxiv.org/abs/2401.17436) | Directly addresses the pre-release case — estimating difficulty "when content has not yet been released and the characteristics of potential future players are not known". Conclusion: **models trained on a combination of cohort statistics and simulated data are most accurate in all scenarios, and artificial neural networks are the most consistent among them** |

The 2024 result is the single most important paper for this project: it says simulated (solver/agent) data alone is *not* the best estimator — it is best **combined with cohort statistics from real players**, which the factory does not yet have.

### 2.3 PCG with quality assurance

The canonical survey is Summerville, Snodgrass, Guzdial, Holmgård, Hoover, Isaksen, Nealen, Togelius, *Procedural Content Generation via Machine Learning (PCGML)*, [arXiv:1702.00539](https://arxiv.org/abs/1702.00539) (v1 2017, v3 2018). It defines PCGML as generating game content with ML models trained on existing content, focuses on **functional** content (platformer levels, maps, IF stories, cards) rather than cosmetic content, and explicitly notes that because PCGML models existing content it is suited to **repair, critique and content analysis** — i.e. quality assurance of generated content — not just autonomous generation. Listed open problems include learning from small datasets, lack of training data and parameter tuning ([arXiv](https://arxiv.org/abs/1702.00539)).

Note the contrast with the factory: the factory uses **solver-based** (search/constraint) generation with a completeness oracle, which the PCGML survey positions as a distinct, older paradigm from ML-based generation ([arXiv](https://arxiv.org/abs/1702.00539)). Solver-verified generation gives a *hard* guarantee (solvable, par known) that PCGML does not.

### 2.4 Agents that find exploits and soft-locks

- EA SEED's DRL framework is explicitly aimed at "find[ing] exploits", unintended gameplay mechanics and bugs, and at map-difficulty testing ([EA SEED](https://www.ea.com/seed/news/automated-game-testing-deep-reinforcement-learning)).
- Curiosity/novelty rewards are the published technique for reaching states that scripted or naive-exploration bots never reach ([arXiv:2103.13798](https://arxiv.org/abs/2103.13798)).
- Commercially, modl.ai's case study on Die Gute Fabrik's *Saltsea Chronicles* is the best small-team analogue: a ~20-person studio with **one dedicated QA person** and a branching narrative too large to test by hand; bots found **states where the player could not proceed, complete freezes, and invisible buttons that still retained interactive functionality**. The team uploaded a build at end of day, **60+ levels were tested overnight**, and programmers fixed from the reports the next morning. No total bug count or quantified time saving is published — **n.a.** ([modl.ai case study](https://modl.ai/testing-content-heavy-games-with-ai-bots)).

### 2.5 LLM-based UI testing and GUI agents

**AUITestAgent** (Fudan University + Meituan In-Store R&D, [arXiv:2407.09018](https://huggingface.co/papers/2407.09018), July 2024) is described as the first automatic, natural-language-driven GUI testing tool for mobile apps that fully automates GUI interaction *and* function verification: dynamically organized agents extract interactions from natural-language requirements, then a multi-dimensional data-extraction strategy pulls verification-relevant data from the interaction trace. Reported **94% verification accuracy** on customized benchmarks, and in field deployment at Meituan it **detected 4 new functional bugs across 10 regression tests over two months** ([Hugging Face papers](https://huggingface.co/papers/2407.09018)).

The broader landscape is mapped in *Large Language Model-Brained GUI Agents: A Survey* ([arXiv:2411.18279](https://arxiv.org/html/2411.18279v1)), which traces the progression from random-based automation → rule-based → script-based → ML/CV and RL → LLM-brained agents, and covers web, mobile, computer and cross-platform agent frameworks, memory, self-reflection, self-evolution and multi-agent designs. Its "random-based automation" category is exactly where Android's Monkey sits, and its "script-based" category is where the factory's XCUITest and Playwright-style bots sit — the factory is one rung below the current research frontier of *goal-directed* GUI agents.

### 2.6 Automated accessibility checkers

| Platform | Tool | What it checks |
|---|---|---|
| Android | **Accessibility Scanner** (uses the Accessibility Test Framework) | Content labels, clickable items, contrast and other accessibility properties, with concrete suggestions ([Android Developers, test your app's accessibility](https://developer.android.com/guide/topics/ui/accessibility/testing)) |
| Android | Compose testing APIs over the **semantics tree** — the same information accessibility services read, so tests reflect real accessibility use cases ([Android Developers](https://developer.android.com/guide/topics/ui/accessibility/testing)) |
| iOS/macOS | **Accessibility Inspector** | Audits for clipped text, unlabeled elements, inappropriate text size and inappropriate color-contrast levels ([Apple, Accessibility Inspector](https://developer.apple.com/documentation/accessibility/accessibility-inspector)) |
| Play | Pre-launch report | Includes accessibility issues among the issue types reported ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/9842757?hl=en)) |

Google's own guidance is that automation is not sufficient: it recommends combining manual testing with accessibility services, analysis tools, automated testing **and** user testing, because analysis tools surface things manual testing misses and user testing yields usability insight neither provides ([Android Developers](https://developer.android.com/guide/topics/ui/accessibility/testing)).

## 3. Human playtesting practice

### 3.1 Sample sizes

| Question the study answers | Recommended n | Source |
|---|---|---|
| Find usability problems (qualitative) | **5 users** per study; 2 can be optimal in very low-overhead agile setups; ~8 sometimes; ~5 per distinct audience group, often 3–4 per group | [NN/g, "How Many Test Users in a Usability Study?"](https://www.nngroup.com/articles/how-many-test-users/) |
| Statistics (quantitative) | **at least 20 users**, more for tight confidence intervals | [NN/g](https://www.nngroup.com/articles/how-many-test-users/) |
| Discover game usability problems | **6 players per playtest, per user type** (6 allows for no-shows and still leaves 5) | [GamesUserResearch.com](https://gamesuserresearch.com/how-many-players-do-i-need-for-a-playtest/) |
| Define players / build personas | **12 per user type**, then check for saturation | [GamesUserResearch.com](https://gamesuserresearch.com/how-many-players-do-i-need-for-a-playtest/) |
| Quantitative game-design questions / surveys | **~100 players** (~10% margin of error); >400 rarely worth the extra processing (~5% MoE) | [GamesUserResearch.com](https://gamesuserresearch.com/how-many-players-do-i-need-for-a-playtest/) |

NN/g's structural advice matters as much as the numbers: extra users are better spent on **additional studies each covering a smaller feature set** than on padding one study ([NN/g](https://www.nngroup.com/articles/how-many-test-users/)). And the games-specific guidance is that even 2–3 testers is worth running, and that a single player can reveal unexpected behavior; *Destiny* ran **over 150 playtests** across development ([GamesUserResearch.com](https://gamesuserresearch.com/how-many-players-do-i-need-for-a-playtest/)).

### 3.2 What studios actually do (survey data)

From the 2023 Playtest Survey: most teams run **two to five external playtests a year** — fewer than one every two months; planning, running and analyzing a study can take **up to three weeks** for dedicated researchers; **almost half of all teams run playtests with 10 or fewer playtesters**, while others run 100–2,000; the most common playtest length is **one to three hours**, ranging from a 15-minute tutorial test to a week-long balance study; the survey's recommendation is that teams usually get more value from **many small moderated studies** than from one large "perfect" playtest ([GamesUserResearch.com, The 2023 Playtest Survey](https://gamesuserresearch.com/the-2023-playtest-survey/)).

### 3.4 Signals collected and how findings are triaged

Collected signals in current practice: screen, voice, touch, face, survey responses, think-aloud transcript, and AI-clustered themes linked to source clips ([PlaytestCloud](https://www.playtestcloud.com/product)). On the analytical side, CHI PLAY work has examined severity of gameplay issues identified via **electrodermal-activity biometrics compared with observation**, arguing for the importance of severity *from the player's perspective* in data-driven evaluation decisions (Halabi, Mirza-Babaei, Uszkoreit, Wallner, *Exploring Severity of Gameplay Issues from Players' Perspective*, **CHI PLAY '20 EA**, Nov 2–4 2020, [ACM DL](https://dl.acm.org/doi/pdf/10.1145/3383668.3419932)).

Reporting practice: a GUR report is a **stand-alone document** meant to make sense to someone who didn't attend the study, or to yourself six months later; the strongest reports share **fewer but more impactful findings** with a narrative thread, and a report is not always the right vehicle — sometimes an email or conversation is ([GamesUserResearch.com, how to write a GUR report](https://gamesuserresearch.com/how-to-write-a-games-user-research-report/)).

## 4. Heuristic / expert review practice in games UX

### 4.1 The heuristic sets

- **Nielsen's 10 usability heuristics** (developed with Rolf Molich, **1990**): visibility of system status; match between system and real world; user control and freedom ("emergency exit"); consistency and standards; error prevention; recognition rather than recall; flexibility and efficiency of use; aesthetic and minimalist design; help users recognize/diagnose/recover from errors; help and documentation ([NN/g](https://www.nngroup.com/articles/ten-usability-heuristics/)).
- **HEP — Heuristic Evaluation for Playability** (Desurvire, Caplan, Toth): a comprehensive playability heuristic set derived from productivity and playtesting heuristics and tailored to video, computer and board games, validated against user testing on an evolving game design. Key finding: **HEP is best suited to general issues in early development with a prototype or mock-up**, and identified qualitative similarities *and* differences versus user testing — the two are complements, not substitutes ([Desurvire et al., HEP paper PDF](https://www.valuesatplay.org/wp-content/uploads/2007/09/desurvireplayabilityheurist.pdf)).
- **PLAY** — the successor iteration, *Game Usability Heuristics (PLAY) for Evaluating and Designing Better Games: The Next Iteration* ([Springer](https://link.springer.com/chapter/10.1007/978-3-642-02774-1_60)).
- **Scoping review of the field**: Ozdowska, Sweetser, Daiiani, *A Scoping Review of Heuristics in Video Games Research: Definitions, Development, Application, and Operationalisation*, ACM, issued **29 Sept 2023** ([ACM DL](https://dl.acm.org/doi/pdf/10.1145/3611035)). Count of distinct heuristic sets reviewed: **n.a.** (not extractable from the fetched page).
- **Game Accessibility Guidelines**: tiered Basic / Intermediate / Advanced across Motor, Cognitive, Vision, Hearing, Speech and General. Basic tier explicitly targets "simple considerations… easy to implement if thought about early enough", and names the **four most commonly complained-about issues: remapping, text size, colorblindness, subtitle presentation** ([Basic list](https://gameaccessibilityguidelines.com/basic/), [Full list](https://gameaccessibilityguidelines.com/full-list/)). Directly relevant Basic criteria for a mobile puzzle game: high contrast between text/UI and background; readable default font size; no essential information conveyed by fixed colour alone; large, well-spaced interactive elements on touch screens; avoid flickering images and repetitive patterns; let players progress through text prompts at their own pace; interactive tutorials; all settings saved/remembered; wide choice of difficulty levels; solicit accessibility feedback ([Basic list](https://gameaccessibilityguidelines.com/basic/)).

### 4.2 How expert review is actually run

NN/g's method: **three to five people independently evaluate the same interface**, each timeboxed to ~1–2 hours, with evaluators kept blind to each other's findings until they finish, and with a deliberately narrow scope (one task, one section, one user group, one device type). A first pass is used purely to learn the system without evaluating ([NN/g, how to conduct a heuristic evaluation](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/)).

In games specifically, Player Research runs **Usability Expert Analysis with at least two researchers** to increase thoroughness and reliability, on any testable material including wireframes, prototypes and GDDs (no playable build required), positioned early to strip "low-hanging fruit" before playtests so that player sessions can go deeper. Notably, they explicitly **do not compare games against a fixed heuristic set**, preferring psychological principles contextualized by the team's stated design intent; issues are prioritized by severity and delivered with actionable solutions ([Player Research](https://www.playerresearch.com/learn/games-user-research-methodology-series-usability-expert-analysis/)).

### 4.3 Severity scales

Nielsen's canonical 0–4 scale:

| Rating | Meaning |
|---|---|
| 0 | Not a usability problem at all |
| 1 | Cosmetic only — fix if spare time |
| 2 | Minor — low priority |
| 3 | Major — important, high priority |
| 4 | Usability catastrophe — imperative to fix before release |

Severity is a **product of three factors: frequency, impact and persistence**. Crucially, "severity ratings from a single evaluator are too unreliable to be trusted"; the **mean of three independent evaluators** is satisfactory for practical purposes ([NN/g, how to rate severity](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/)).

### 4.4 Issue-report schema used in games

Steve Bromley's dissected real GUR report structure gives the practical field list:

| Field | Purpose |
|---|---|
| Title page | Game, date, reviewer, **method** |
| Objectives | What the research aimed to learn |
| Method | How it was run; formal methodologies (e.g. heuristics) introduced; explicitly notes when only an expert reviewer played and no real players participated |
| Prioritisation key | The severity/priority scheme, introduced up front |
| Positives | Well-implemented features — "knowing what not to change can be just as important" — with screenshots and impact |
| Issue description | The problem itself |
| Evidence | Screenshots supporting the issue |
| Causes | The reasons it occurs; multiple causes listed and ordered by most impactful |
| Impact | How it affects players |
| Recommendation | Deliberately *not* provided per issue in this format; solutions generated in a workshop with the dev team |
| Grouping | Issues grouped by theme; groups ordered so the most severe appear first |

([Steve Bromley, "What's in a games user research report?"](https://www.stevebromley.com/blog/2017/03/08/whats-in-a-games-user-research-report/))

### 4.5 Prioritization frameworks

**RICE** (Intercom): Reach = how many people affected per period, measured in people/events per time period from real product metrics; Impact on a per-person multiple-choice scale **3 = massive, 2 = high, 1 = medium, 0.5 = low, 0.25 = minimal**; Confidence **100% high / 80% medium / 50% low**, below 50% is "total moonshot"; Effort in **person-months** (0.5 for well under a month), dividing the total because more effort is bad. The combined score measures **"total impact per time worked"** ([Intercom](https://www.intercom.com/blog/rice-simple-prioritization-for-product-managers/)).

**MoSCoW** (Agile Business Consortium): Must Have = the Minimum Usable SubseT — no point deploying without it, or it's illegal/unsafe/non-viable; Should Have = important, painful to omit but a workaround exists, delivery not guaranteed; Could Have = desirable, the main pool of contingency, first to be cut; Won't Have this time = explicitly recorded to prevent informal scope creep. Effort guidance: **Must Have effort should typically not exceed 60%** of the increment, with **~20% Could Have**; above 60% Musts introduces risk of failure unless estimates, approach, team maturity and environment are all favorable ([Agile Business Consortium](https://www.agilebusiness.org/resource/what-is-moscow-prioritization/)).

### 4.6 Verdict on the factory's schemas

**Critic schema: `{area, severity, text}`.** Insufficient as-is, on three verifiable grounds:

1. **Severity is unreliable from one rater.** The factory's critic is a single evaluator. NN/g states single-evaluator severity ratings are "too unreliable to be trusted" and recommends the mean of **three independent evaluators** ([NN/g](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/)). Standard heuristic evaluation likewise uses **3–5 independent evaluators** ([NN/g](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/)); games practice uses at least two ([Player Research](https://www.playerresearch.com/learn/games-user-research-methodology-series-usability-expert-analysis/)).
2. **Severity is a composite that isn't being decomposed.** Frequency, impact and persistence should be captured separately so the composite can be recomputed and audited ([NN/g](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/)).
3. **No evidence, cause, impact, positives or heuristic reference.** Professional reports carry evidence (screenshots), explicit causes ordered by impact, explicit player impact, and an equally explicit positives section ([Steve Bromley](https://www.stevebromley.com/blog/2017/03/08/whats-in-a-games-user-research-report/)); the method itself should be stated in the artifact ([Steve Bromley](https://www.stevebromley.com/blog/2017/03/08/whats-in-a-games-user-research-report/)).

**Breaker schema: REPRO / EXPECTED / ACTUAL.** This is a sound *defect* schema — it maps onto the automated-testing definition of a failure, where an explicit assertion about app state distinguishes pass from fail ([Firebase Test Lab test types](https://firebase.google.com/docs/test-lab/android/get-started)) — but it is missing the routing and reproducibility metadata that store-facing QA requires.

**Missing fields, ranked:**

| # | Missing field | Why, with source |
|---|---|---|
| 1 | **Severity decomposed into frequency × impact × persistence** | Composite severity from one rater is untrustworthy ([NN/g](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/)) |
| 2 | **Independent second/third rater (or 3 diverse persona runs) + inter-rater agreement** | 3–5 independent evaluators is the standard; games practice uses ≥2 ([NN/g](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/), [Player Research](https://www.playerresearch.com/learn/games-user-research-methodology-series-usability-expert-analysis/)) |
| 3 | **Evidence artifact** (screenshot / video / trace / seed) | Reports attach screenshots per issue ([Steve Bromley](https://www.stevebromley.com/blog/2017/03/08/whats-in-a-games-user-research-report/)); Play's pre-launch report attaches screenshot, video and stack trace per issue ([Play Console](https://support.google.com/googleplay/android-developer/answer/9844487?hl=en)) |
| 4 | **Build / version / device / OS / locale** | Play's issue detail carries device name, screen size, Android version, RAM, ABI and locale ([Play Console](https://support.google.com/googleplay/android-developer/answer/9844487?hl=en)) |
| 5 | **Cause(s), ordered by most impactful** | Explicit report field ([Steve Bromley](https://www.stevebromley.com/blog/2017/03/08/whats-in-a-games-user-research-report/)) |
| 6 | **Player impact statement** (distinct from severity) | Explicit report field ([Steve Bromley](https://www.stevebromley.com/blog/2017/03/08/whats-in-a-games-user-research-report/)) |
| 7 | **Heuristic reference** (which Nielsen/PLAY/GAG criterion is violated) | Heuristic evaluation records one observation per line **with its corresponding heuristic** ([NN/g](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/)) |
| 8 | **Positives** | Explicitly recommended: knowing what not to change matters ([Steve Bromley](https://www.stevebromley.com/blog/2017/03/08/whats-in-a-games-user-research-report/), [Player Research](https://www.playerresearch.com/learn/games-user-research-methodology-series-usability-expert-analysis/)) |
| 9 | **Reproducibility rate** (n hits / n attempts, plus seed) | Monkey's `-s <seed>` makes stress runs repeatable ([Android Monkey](https://www.dre.vanderbilt.edu/~schmidt/android/android-4.0/out/target/common/docs/doc-comment-check/guide/developing/tools/monkey.html)); Play's report counts "number of times the issue was detected" and "number of devices" ([Play Console](https://support.google.com/googleplay/android-developer/answer/9844487?hl=en)) |
| 10 | **Theme/grouping key** so issues can be grouped and groups ordered by severity | ([Steve Bromley](https://www.stevebromley.com/blog/2017/03/08/whats-in-a-games-user-research-report/)) |
| 11 | **Effort estimate → RICE or MoSCoW label** to make DO NOW / DESIGN CHANGE / SKIP defensible | RICE = impact per time worked ([Intercom](https://www.intercom.com/blog/rice-simple-prioritization-for-product-managers/)); MoSCoW caps Must-Have effort at ~60% ([Agile Business Consortium](https://www.agilebusiness.org/resource/what-is-moscow-prioritization/)) |

The existing DO NOW / DESIGN CHANGE / SKIP triage is essentially a three-bucket MoSCoW without the "Won't have **this time**" discipline of recording the rejected item to prevent informal reintroduction later ([Agile Business Consortium](https://www.agilebusiness.org/resource/what-is-moscow-prioritization/)) — SKIP items should be logged, not dropped.

## 5. Difficulty tuning without telemetry

What is verifiably possible pre-launch:

| Technique | Evidence | Applicability here |
|---|---|---|
| **Solver/agent move-count as a completion-rate proxy** | Moves in roughly the **best 5% of RL agent runs** is the strongest predictor of human completion rate in a mobile puzzle game ([arXiv:2306.14626](https://arxiv.org/abs/2306.14626)) | Directly implementable: the BFS solver already yields optimal par; what's missing is a *distribution* of near-optimal runs, not a single optimum |
| **Distribution of in-level actions, not just P(win)** | P(completion) is too thin; parametric models of the action distribution explain difficulty in the vast majority of *Lily's Garden* levels ([CoG 2021](https://dl.acm.org/doi/10.1109/CoG52621.2021.9619050)) | Needs a stochastic/human-like player, not an optimal solver |
| **Human-like (not optimal) agents** | King's bot deliberately picks the action a human would most likely take, not the best one, and is validated by a linear relationship between bot estimates and real difficulty ([GamesIndustry.biz](https://www.gamesindustry.biz/how-king-is-using-ai-to-speed-up-development-of-new-candy-crush-levels)); Ubisoft's CARMI emulates player play-styles on unseen levels from summary data ([HAL](https://hal.science/hal-03957672v1/document)) | The single biggest modelling gap: an optimal BFS solver measures *solvability and par*, not *human difficulty* |
| **Combine simulated data with cohort statistics** | Best accuracy in all scenarios comes from models trained on cohort statistics **plus** simulated data, with ANNs most consistent ([arXiv:2401.17436](https://arxiv.org/abs/2401.17436)) | Impossible until some human data exists — the strongest argument for a small paid playtest panel now |
| **Expert panel before players** | Expert analysis needs no playable build, is cheaper/faster than playtests, and clears low-hanging fruit so later playtests go deeper ([Player Research](https://www.playerresearch.com/learn/games-user-research-methodology-series-usability-expert-analysis/)); HEP is best for general issues early with a prototype ([Desurvire et al.](https://www.valuesatplay.org/wp-content/uploads/2007/09/desurvireplayabilityheurist.pdf)) | The AI critic is a cheap simulacrum of this; ≥2–3 independent raters is the standard |
| **A/B readiness** | Remote Config lets you "tune the game difficulty curve in near real time" and roll features out gradually without an app update ([Unity Remote Config](https://docs.unity.com/en-us/remote-config)); Firebase experiments start on a small percentage and ramp, tracking crashes, retention and revenue alongside the goal ([Firebase A/B Testing](https://firebase.google.com/docs/ab-testing)) | Ship the *plumbing* (level order, par, star bands, hint costs as remote parameters) before launch even with no experiments running |

**How fast studios re-tune after soft launch.** Soft launch is explicitly staged: **alpha** tests whether the core loop and technology work; **beta** tests the meta loop, UA, server scalability and monetization. a16z counts **100+ games soft-launched on the App Store and 600+ on Google Play in a single month**, notes that acquiring a churned player is typically **5–10× more expensive** than acquiring a new one, warns that no test country accurately simulates another (retention/monetization are only "directionally" useful), and recommends acquiring users at scale from lower-cost geographies to stress-test servers and get **FPS, crash rates/DAU, crashes/crasher and latency** from long-tail devices — pointing explicitly at the Android Vitals dashboard ([a16z, "Play to Win: Mobile Game Soft Launch Best Practices"](https://a16z.com/mobile-game-soft-launch/)). Practical cautions: "good" metric values vary hugely by genre, and player behavior differs sharply by country, so a cheaper market like the Philippines or Malaysia behaves differently from a target-similar market like Australia, Canada, Sweden or the Netherlands ([Game Developer, "4 Soft Launch Metrics That Matter"](https://www.gamedeveloper.com/business/4-soft-launch-metrics-that-matter-to-the-success-of-your-mobile-game)). ## 6. A/B testing for level order and difficulty in mobile puzzle

### 6.1 What studios test and at what volume

Supercell — ~300M monthly players — deliberately runs **fewer than a hundred A/B tests per quarter company-wide**, roughly **10–20 experiments per game per quarter**, each chosen because the answer matters; **retention is the north star and revenue is explicitly not the first goal**; the company frames itself as *hypothesis-driven* rather than data-driven, with the designer's creative conviction written down as a falsifiable claim first. They also **announce tests to players in advance** and guarantee **make-up events** for players who got the worse variant, on the reasoning that a player in a losing variant loses part of the thing they came for ([GrowthBook / Supercell](https://www.growthbook.io/blog/a-b-testing-300-million-players-without-breaking-their-trust-the-supercell-approach)). For a solo dev, the transferable lesson is not the tooling — it is that even at that scale, experiment *volume* is low and *hypothesis quality* is the constraint.

Unity's canonical documented example is literally difficulty A/B testing: five groups A–E receiving XP-to-level thresholds of **100 / 80 / 60 / 50 / 30**, with players randomly assigned and the assigned group fetched from Remote Config at session start ([Unity, A/B testing with Remote Config](https://docs.unity.com/ugs/solutions/manual/ABTest)).

### 6.2 Tooling comparison

| Tool | Documented capability | Notes |
|---|---|---|
| **Firebase Remote Config + A/B Testing** | Variants over parameters; AND-chained targeting on app version, Analytics audiences (e.g. "crashing users") and custom user properties; goal = Analytics event or conversion funnel; secondary tracking of crashes, retention, revenue; ramp from small % to full base after a "leader" emerges ([Firebase](https://firebase.google.com/docs/ab-testing)) | Statistical inference method and minimum sample size are **not stated** on the overview page — **n.a.** ([Firebase](https://firebase.google.com/docs/ab-testing)) |
| **Unity Remote Config / UGS** | Namespaced key–value parameters, Game Overrides per player, difficulty-curve tuning in near real time, gradual feature rollout with impact monitoring, region/segment targeting, event on/off, no app update ([Unity](https://docs.unity.com/en-us/remote-config)); worked A/B sample with 5 groups ([Unity](https://docs.unity.com/ugs/solutions/manual/ABTest)) | Requires Analytics, Authentication, Cloud Save, Cloud Code alongside ([Unity](https://docs.unity.com/ugs/solutions/manual/ABTest)) |
| **GameAnalytics** | A/B testing for UI layouts/placements, **mechanics, difficulty levels and progression to increase retention**, pricing, new-feature impact, ad placements ([GameAnalytics docs](https://docs.gameanalytics.com/features/ab-testing/)) | Remote-config details, requirements and traffic allocation are **not stated** on that page — **n.a.** |
| **Amplitude** | Sample-size calculators exist but are explicitly "a ballpark estimate rather than ground truth" ([Amplitude](https://amplitude.com/blog/sample-size-calculator-assumptions)) | See pitfalls below |
| **Optimizely** | Stats Engine removes the need to pre-compute sample size and declares winners/losers as evidence accrues; default significance level **90%**; minimum run of **one business cycle = 7 days** ([Optimizely](https://support.optimizely.com/hc/en-us/articles/4410283969165-How-long-to-run-an-experiment)) | Web-first, but the duration rule is universal |
| **Custom** | — | Riot builds custom CI/CD and test infrastructure in-house ([Riot](https://www.riotgames.com/en/news/legends-runeterra-cicd-pipeline)); Supercell runs a central experimentation platform team ([GrowthBook](https://www.growthbook.io/blog/a-b-testing-300-million-players-without-breaking-their-trust-the-supercell-approach)) |

### 6.3 Sample size and the pitfalls that actually bite

- **Minimum duration**: run at least **one business cycle (7 days)** to absorb weekday/weekend and seasonality effects ([Optimizely](https://support.optimizely.com/hc/en-us/articles/4410283969165-How-long-to-run-an-experiment)).
- **Underpowered tests**: a large observed improvement with 0% statistical significance means the test simply hasn't had enough visitors; decisions from underpowered tests produce improvements "unlikely to hold up" ([Optimizely](https://support.optimizely.com/hc/en-us/articles/4410283969165-How-long-to-run-an-experiment)).
- **Effect size drives cost**: fewer visitors are needed to detect large differences; higher baseline conversion rates need smaller samples; small differences take much longer; highly variable data needs more data ([Optimizely](https://support.optimizely.com/hc/en-us/articles/4410283969165-How-long-to-run-an-experiment)).
- **Calculator assumptions that are routinely violated** ([Amplitude](https://amplitude.com/blog/sample-size-calculator-assumptions)):

| Assumption | Failure mode | Mitigation |
|---|---|---|
| Identical behavior over time | Seasonality; a short test captures an uneven subset of users | Graph lift vs exposure date; run an integer number of business cycles |
| CLT applies cleanly | Long-tailed metrics (revenue, session length) skew the sample mean away from normality | Bootstrap/resample and inspect the histogram |
| Only one hypothesis tested | Multiple comparisons inflate false positives | Bonferroni, Tukey, Dunnett or Scheffé |
| Static eligibility pool | Pool depletes and refills, changing cohort makeup mid-test | Plot cumulative exposures; run until equilibrium; discard pre-equilibrium data |

For a 40-level premium-ish puzzle game with no telemetry, the binding constraint is DAU, not statistics: a level-order A/B test with a meaningful minimum detectable effect on level-3-completion is not runnable at indie traffic in a 7-day cycle. The pre-launch move is to make level order, par, star bands and hint economics **remote-configurable** so that the experiment becomes possible later without a client update ([Unity](https://docs.unity.com/en-us/remote-config), [Firebase](https://firebase.google.com/docs/ab-testing)).

## 8. Gap analysis

### 8.1 What this factory does that exceeds typical indie practice

| # | Practice | Why it exceeds the norm |
|---|---|---|
| 1 | **A completeness oracle**: BFS solver proves *every* level solvable and computes par | Play's own automated crawler only explores for "several minutes" with taps and swipes ([Play Console](https://support.google.com/googleplay/android-developer/answer/9842757?hl=en)); modl.ai's flagship indie case study is about a 20-person studio needing AI bots because a **single QA person** couldn't cover the content ([modl.ai](https://modl.ai/testing-content-heavy-games-with-ai-bots)). A solver-proved 100% solvability guarantee is stronger than anything an exploratory bot provides |
| 2 | **Byte-identical deterministic regeneration + optimal-solution replay through the real engine** | Riot needed roughly a year of multi-engineer work to reach gameplay determinism and the record/playback/validate tooling it enables ([Riot](https://www.riotgames.com/en/news/determinism-league-legends-implementation)) |
| 3 | **A rule-parity oracle** (engine vs tools over 200 random positions) | This is differential/metamorphic testing against an independent implementation. Riot frames divergence detection as comparing runtime state across executions with fixed inputs ([Riot](https://www.riotgames.com/en/news/determinism-league-legends-implementation)); most indie projects have no second implementation to compare against at all |
| 4 | **A ~2-minute commit gate with 109 named checks** | Riot's per-build gate is ~18 minutes for 5,500 tests ([Riot](https://www.riotgames.com/en/news/automated-testing-league-legends)); LoR's full pipeline averages ~60 minutes ([Riot](https://www.riotgames.com/en/news/legends-runeterra-cicd-pipeline)). A 2-minute gate is in the right regime for the scope and beats what almost any solo project runs |
| 5 | **Two-platform bot coverage** (headless Chromium + iOS XCUITest with an in-app autoplay bot) | This is exactly the "game loop / demo mode" pattern Firebase Test Lab formalizes as the scalable way to verify a game ([Firebase](https://firebase.google.com/docs/test-lab/android/get-started)) — built independently |
| 6 | **Accessibility and motion checks inside CI** (contrast ratios, reduced-motion behaviour) | Contrast and reduced motion are Basic-tier accessibility guidelines and among the most-complained-about issue classes ([GAG Basic](https://gameaccessibilityguidelines.com/basic/)); most teams check them manually with Accessibility Scanner or Inspector, if at all ([Android](https://developer.android.com/guide/topics/ui/accessibility/testing), [Apple](https://developer.apple.com/documentation/accessibility/accessibility-inspector)) |
| 7 | **Regression check added per fix, mandated** | Riot attributes automation misses to lack of coverage rather than bad tests ([Riot](https://www.riotgames.com/en/news/automated-testing-league-legends)); a per-fix coverage ratchet is exactly the countermeasure |
| 8 | **Zero-network and bundle-freshness assertions** | Removes a whole class of Apple 2.1 "backend not live / broken links" rejection risk before submission ([Apple rejections](https://developer.apple.com/app-store/review/rejections/)) |
| 9 | **Adversarial AI persona filing REPRO/EXPECTED/ACTUAL** | The direction of travel in research (AUITestAgent reports 94% verification accuracy and found 4 new functional bugs in 10 regression tests over two months at Meituan ([arXiv:2407.09018](https://huggingface.co/papers/2407.09018))) — very few indie teams run anything like it |

### 8.2 Ranked list of missing practices

| Rank | Missing practice | Cost | Why it ranks here (source) |
|---|---|---|---|
| 1 | **Any human player, ever.** Run ~6 unmoderated sessions with target players | ~$414 at $69/participant ([GamesUserResearch](https://gamesuserresearch.com/top-remote-playtest-platforms-for-unmoderated-testing/)); or 1 free player at Antidote ([Antidote](https://antidote.gg/platform-features/)) | 6 players per user type is the standard for finding usability problems ([GamesUserResearch](https://gamesuserresearch.com/how-many-players-do-i-need-for-a-playtest/)); HEP research explicitly found expert heuristics identify *different* issues than user testing and are best combined ([Desurvire et al.](https://www.valuesatplay.org/wp-content/uploads/2007/09/desurvireplayabilityheurist.pdf)). Everything about perceived difficulty, comprehension and fun is currently unmeasured |
| 2 | **Human-like / stochastic difficulty estimation, not optimal-par difficulty** | Days of work, no ML required | Human completion rate correlates with the **best-5%-of-runs move count**, not the optimum ([arXiv:2306.14626](https://arxiv.org/abs/2306.14626)); difficulty is better described by the **distribution of in-level actions** ([CoG 2021](https://dl.acm.org/doi/10.1109/CoG52621.2021.9619050)); King's bot deliberately plays human-like rather than optimally ([GamesIndustry.biz](https://www.gamesindustry.biz/how-king-is-using-ai-to-speed-up-development-of-new-candy-crush-levels)). A "difficulty sawtooth" asserted from optimal par may not be a sawtooth for humans |
| 3 | **Crash/ANR instrumentation + vitals budget as an explicit release gate** | Hours | 1.09% crash / 0.47% ANR are store-visibility thresholds evaluated over a rolling 28 days ([Android Developers Blog](https://android-developers.googleblog.com/2022/10/raising-bar-on-technical-quality-on-google-play.html), [Play Console](https://support.google.com/googleplay/android-developer/answer/9844486?hl=en)); Crashlytics velocity alerts are **off by default** and must be enabled ([Firebase](https://firebase.google.com/docs/crashlytics/velocity-alerts)) |
| 4 | **Real-device matrix coverage (Android especially) + Game Loop wiring** | Free on Play alpha/beta ([Firebase](https://firebase.google.com/docs/test-lab/android/get-started)) | Per-device bad-behavior thresholds are 8% at launch and expected to tighten ([Android Developers Blog](https://android-developers.googleblog.com/2022/10/raising-bar-on-technical-quality-on-google-play.html)); the pre-launch report already surfaces per-device stack traces, screenshots, video and average FPS from game loops ([Play Console](https://support.google.com/googleplay/android-developer/answer/9844487?hl=en)). The current gate proves the game is *correct*, not that it *runs* on a Galaxy A-series |
| 5 | **Play closed-testing compliance: 12 testers × 14 continuous days** | Recruitment time | Blocking prerequisite for production access on personal accounts created after 13 Nov 2023 ([Play Console](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en)). This must start ~3 weeks before the intended launch date |
| 6 | **Phased/staged release plan with defined halt criteria** | Free | Apple's 7-day 1/2/5/10/20/50/100% ladder with 30 cumulative pause days ([Apple](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases/)); Play halt/resume ([Play](https://support.google.com/googleplay/android-developer/answer/6346149?hl=en-GB)). Define the abort thresholds (e.g. crash rate) *before* day 1 |
| 7 | **Multi-rater critic + decomposed severity (frequency/impact/persistence) + inter-rater agreement** | Cheap — extra persona runs | Single-rater severity is "too unreliable to be trusted"; mean of three is satisfactory ([NN/g](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/)); heuristic evaluation standard is 3–5 independent evaluators ([NN/g](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/)) |
| 8 | **Richer issue schema**: evidence artifact, build/device/OS, cause(s), player impact, heuristic reference, positives, reproducibility rate, theme grouping | Cheap | See §4.6 table; sourced to ([Steve Bromley](https://www.stevebromley.com/blog/2017/03/08/whats-in-a-games-user-research-report/)), ([NN/g](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/)), ([Play Console](https://support.google.com/googleplay/android-developer/answer/9844487?hl=en)) |
| 9 | **Remote config plumbing for level order, par, star bands, hint economy** | Days | Difficulty-curve tuning in near real time without an app update ([Unity](https://docs.unity.com/en-us/remote-config)); gradual rollout with crash/retention monitoring ([Firebase](https://firebase.google.com/docs/ab-testing)). Retrofitting this after a bad launch costs a full review cycle per tweak |
| 10 | **Randomized / fuzz UI stress with recorded seeds (soak testing)** | ~1 day | Monkey generates repeatable pseudo-random streams under `-s <seed>` and reports crashes, unhandled exceptions and ANRs ([Android Monkey](https://www.dre.vanderbilt.edu/~schmidt/android/android-4.0/out/target/common/docs/doc-comment-check/guide/developing/tools/monkey.html)). The 109 checks test *anticipated* interactions; the undo/rescue/modal/ad-grant state machine is exactly where unanticipated interleavings hide |
| 11 | **Formal accessibility audit pass** (Accessibility Scanner + Accessibility Inspector) beyond contrast/reduced-motion | Hours | Automated tools check labels, clickable items, contrast, clipped text and text size ([Android](https://developer.android.com/guide/topics/ui/accessibility/testing), [Apple](https://developer.apple.com/documentation/accessibility/accessibility-inspector)); Basic-tier GAG adds text size, remapping/sensitivity, settings persistence, difficulty options, self-paced text prompts, interactive tutorials, "no info by colour alone" ([GAG Basic](https://gameaccessibilityguidelines.com/basic/)) |
| 12 | **Explicit heuristic-set mapping** (Nielsen 10 / PLAY / GAG) driving the critic's review rubric | Hours | Heuristic evaluation records each observation against its corresponding heuristic ([NN/g](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/)); the 10 heuristics are the base set ([NN/g](https://www.nngroup.com/articles/ten-usability-heuristics/)); HEP/PLAY is the games-specific extension ([Desurvire et al.](https://www.valuesatplay.org/wp-content/uploads/2007/09/desurvireplayabilityheurist.pdf), [Springer PLAY](https://link.springer.com/chapter/10.1007/978-3-642-02774-1_60)) |
| 13 | **Apple 2.1 pre-submission checklist as a CI artifact** | Hours | >40% of unresolved review issues are Guideline 2.1 ([Apple](https://developer.apple.com/app-store/review/rejections/)); guidelines require scrubbed placeholders, working URLs, on-device stability testing, complete IAP visible to the reviewer, and loot-box odds disclosure ([Apple](https://developer.apple.com/app-store/review/guidelines/)) |
| 14 | **Effort estimate + RICE/MoSCoW label on triage, with SKIP items logged not dropped** | Hours | RICE = total impact per time worked, effort in person-months ([Intercom](https://www.intercom.com/blog/rice-simple-prioritization-for-product-managers/)); "Won't have **this time**" items are recorded specifically to prevent informal reintroduction ([Agile Business Consortium](https://www.agilebusiness.org/resource/what-is-moscow-prioritization/)) |
| 15 | **Soft-launch / geo-test plan with pre-declared kill and re-tune criteria** | Weeks | Alpha tests core loop and tech, beta tests meta loop, UA, scalability, monetization; churned players cost 5–10× to re-acquire; long-tail Android devices only show up at scale ([a16z](https://a16z.com/mobile-game-soft-launch/)); "good" metrics vary hugely by genre and country ([Game Developer](https://www.gamedeveloper.com/business/4-soft-launch-metrics-that-matter-to-the-success-of-your-mobile-game)) |
| 16 | **Post-launch cohort statistics fused with simulated data for difficulty modelling** | Post-launch | The most accurate difficulty estimates in all scenarios come from **cohort statistics + simulated data**, ANNs most consistent ([arXiv:2401.17436](https://arxiv.org/abs/2401.17436)). This is the natural end-state for the solver the factory already has |
| 17 | **A/B experiments on level order / difficulty** | Post-traffic | Minimum 7-day business cycle and real underpowering risk ([Optimizely](https://support.optimizely.com/hc/en-us/articles/4410283969165-How-long-to-run-an-experiment)); calculator assumptions routinely violated ([Amplitude](https://amplitude.com/blog/sample-size-calculator-assumptions)); even Supercell runs only 10–20 per game per quarter ([GrowthBook](https://www.growthbook.io/blog/a-b-testing-300-million-players-without-breaking-their-trust-the-supercell-approach)) |

### 8.3 One-line summary of the gap

The factory is, verifiably, **stronger than typical indie practice on correctness and determinism** — a solver-backed completeness oracle, byte-identical regeneration, a differential rule oracle and a fast per-commit gate are things AAA studios spend engineer-years building ([Riot](https://www.riotgames.com/en/news/determinism-league-legends-implementation), [Riot](https://www.riotgames.com/en/news/automated-testing-league-legends)) — and **weaker than typical indie practice on everything that requires a human or a device**: no real player has ever played it, difficulty is measured by an optimal solver rather than a human-like one ([arXiv:2306.14626](https://arxiv.org/abs/2306.14626)), there is no crash/ANR instrumentation against published store thresholds ([Android Developers Blog](https://android-developers.googleblog.com/2022/10/raising-bar-on-technical-quality-on-google-play.html)), no device matrix ([Firebase](https://firebase.google.com/docs/test-lab)), and no compliance path through Play's 12-tester/14-day closed test ([Play Console](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en)). Six paid playtesters and a Test Lab run would close more risk than another 109 assertions.
